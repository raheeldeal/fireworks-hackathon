# Decisions (chronological)

1. **Data source.** The BFCL paths in the brief (`berkeley-function-call-leaderboard/data/BFCL_v3_*.json`) 404; the repo moved them to `bfcl_eval/data/BFCL_v4_*.json`. Used v4 simple_python, multiple, live_simple, live_multiple. simple_java / simple_javascript skipped (non-JSON argument syntax).
2. **Ground truth with multiple acceptable values.** BFCL stores a list of acceptable values per argument and `""` for "may be omitted". The brief's "exact match after normalization" is implemented as: the predicted value must equal one acceptable value after normalization; arguments allowing `""` may be omitted; extra arguments are wrong. For training labels one canonical call is derived: first acceptable value per required argument, optional arguments omitted.
3. **Test composition** is weighted toward the harder categories (70 live_multiple, 50 multiple) because the point of the night is to find headroom. Rows >8,000 chars dropped to keep kimi-k3 and glm-5p3 affordable. Seed 20261101.
4. **Leak check** flagged 6 train rows sharing a user message with test rows (BFCL reuses queries with different tool sets). Test set untouched; those 6 rows were removed from train (394 remain, 0 overlap).
5. **Tool names.** The tool API rejects dots (`math.factorial`); names are sanitized to `[A-Za-z0-9_-]` in `tools` mode and mapped back before scoring. The scorer treats `.` and `_` as equal.
6. **Few-shot** examples are rendered as text in the system prompt in both modes (tools mode has no clean multi-tool-set message form).
7. **Routing** is computed offline from per-row results of the small and large runs (same test set, same prompt) rather than by re-calling: escalate when the small answer is invalid or its mean answer-token logprob is below a threshold; cost and latency are additive for escalated rows.
8. **SFT base model.** `firectl` is not installed; the REST model endpoint reports `tunable: false` for both nemotron-lightning-3p5-30b-a3b and glm-5p3-flash (glm-5p3-flash is also a 320B MoE, not <16B). Managed SFT output can only be served on a dedicated deployment (docs: "Serverless deployment is not supported for LoRA models"), which rule 3 forbids. The docs state Muse Glimmer 30B LoRA SFT is free via UI and Serverless Training API until 2026-11-30 (docs.fireworks.ai/fine-tuning/models.md and .../cookbook/muse-glimmer.md) and serverless checkpoints can be sampled with no deployment. Plan: train Muse Glimmer 30B LoRA SFT on the Serverless Training API with the cookbook starter (`vendor/cookbook/training/examples/sft/muse_glimmer_starter.py`, which refuses to launch unless the promotion is active), then score the checkpoint on the locked test set with my own sampler script in the plain-prompt JSON format. Evaluation sampling is paid at the published per-token rates (prefill $1.96/M, sample $4.88/M) and is logged in the ledger. Nemotron-lightning is deprecated 2026-11-07 per the model endpoint; noted for the pitch.
9. **Spend plan ($3 cap).** glm-5p3 json-mode and kimi-k3 limited to 100 rows; kimi-k3 tools mode only (100 rows). max_tokens 1024 so reasoning models can finish.
10. **Account suspension (22:04).** Every call started returning HTTP 412 "Account raheeldeal is suspended, possibly due to reaching the monthly spending limit or failure to pay past invoices" after my probes at 21:58 succeeded. All paid work is blocked until the user raises the limit at https://fireworks.ai/account/billing. Everything that needs no API call was finished; the API phases are marked partial in RESULTS.md with the exact commands to resume.

11. **Nemotron needs a 4096-token output budget (2026-11-02 00:00).** Every one of the 42 "invalid" baseline rows was the model spending all 1024 output tokens on hidden reasoning (`reasoning_tokens` = 1024, empty `tool_calls`). PROTOCOL asks for max_tokens 512+, so 1024 met the rule but hid the model's real accuracy. 20-row probe at 4096: 20/20, ~330 reasoning tokens per row. All nemotron rows are rerun at 4096 (`*_mt4096`); the 1024 rows stay in the table, labelled, as a gotcha. The rubric-prompt "regression" at 1024 was the same truncation (more to reason about, more rows cut off), so the prompt lever is re-measured at 4096 before any conclusion.

12. **Ledger bug: short model names priced at $0.** `run_eval.py` keyed prices on the full `accounts/fireworks/models/...` id; passing the short name silently logged $0. Fixed: short names are normalized and an unpriced model now aborts. The two 20-row probes and the three reruns launched with short names got corrected ledger lines computed from their token counts at the PROTOCOL rates (noted in the `note` column).

13. **Best config and SFT verdict (00:45).** `reasoning_effort: none` + `tool_choice: required` on nemotron is the headline (91.0% ± 0.5%, $0.054/1k, 0.40 s), found after the 4096-token reruns showed the baseline gap was truncation. Rubric, few-shot, JSON-schema and routing were all measured and add nothing on top. The SFT (Muse Glimmer, +24 points to 89.5%) is reported as a second, training-based route to the same place rather than the headline, because it costs 40 minutes and a training pipeline versus two request flags, and its sampler price is not a serving price.
