# Decisions (natural language → regex run, 2026-11-01 night)

Calls I made without asking, in the order they came up.

1. **Dataset dialect.** The deep-regex gold regexes are a 2013/2016 DSL: `&` means set intersection and `~` means complement, neither of which Python `re` can run. 39% of rows use them. I dropped those rows instead of translating them (translation via lookaheads only works at the top level, and would have made the gold strings depend on my translation code). Usable rows: KB13 612/824, NL-RX-Synth 6052/10000. Consequence: the test set is a little easier than the full dataset, because intersection/negation prompts ("lines without 'x'") are the hardest ones. Noted in RESULTS.md headroom verdict.

2. **Test set from KB13 only.** KB13 descriptions are human-written ("lines using words ending in 'ness'"); NL-RX-Synth descriptions are template-generated and ambiguous ("lines with a number or a lower-case letter, 5 or more times") with gold that often reads as a parse of the template rather than the English. A model judged against NL-RX-Synth gold would be scored on guessing the template's precedence rules. So test = 200 KB13 rows, one per unique gold regex, fixed shuffle seed 13. NL-RX-Synth is used only to top up the training set.

3. **Gold cleaning.** I read all 200 candidate test rows. Two had gold that contradicts the description (kb13-213, kb13-773); they are listed with reasons in `data/excluded_gold.txt` and the builder skips them. Rows with "at least N" vs "exactly N" ambiguity were kept: the dataset's convention is "at least" when the description says "N words", and the negatives, generated from the gold, encode that convention. Two more rows were dropped automatically because the builder could not find 10 unique positive strings for them (logged in `raw/build_data.log`).

4. **String generation.** `exrex` does not understand `\b`, so every exrex candidate is checked with `re.fullmatch` against the gold before it becomes a positive (rejection sampling, up to 400 tries, repeat limit cycling 1..6). For `\b` patterns, a second candidate with punctuation swapped for spaces is also tried. Negatives are mutations of positives (delete/insert/replace/swap a char, truncate, case flips, strip digits/letters/spaces, double the string, empty string, random string, a string from another row), kept only when the gold rejects them. Per-row RNG is seeded by the row id, so the files are byte-reproducible.

5. **Scoring timeout.** Python's `re` cannot be interrupted by a signal mid-match, so each match runs in a forked child with a 1 s deadline (`score.py`). About 4000 forks per 200-row eval, roughly 20 s of overhead. A timeout counts as a wrong string, not as invalid (the regex compiled; it is just unusable).

6. **Fine-tuning path (the big one).**
   - `firectl model get` / the models API: every LoRA-tunable base under 16B (qwen3-0p6b, ministral-3-3b, llama-v3p2-3b, qwen3-4b, qwen3-4b-instruct-2507, qwen3-8b, llama-v3p1-8b, qwen3p5-9b, qwen3-14b) has `Supports Serverless Lora: false`. The managed SFT doc says an on-demand (dedicated) deployment is "the only supported method for serving trained models". Protocol rule 3 forbids that, so a managed SFT job on a <16B model **cannot be scored tonight**. Per rule 3 I document the exact commands and mark the row "not scored (dedicated deployment required)".
   - The only tunable bases with serverless LoRA serving are glm-5p3-flash (320B total / 18B active, managed LoRA SFT priced at the >300B tier, $10/M training tokens) and ultramarine-1-flash-us. Both break the "under 16B" rule for paid SFT, so not used.
   - **Free and scorable:** the docs (`fine-tuning/models.md`) and the pricing page both say "Muse Glimmer 30B SFT is free via UI and Serverless Training API until 11/30, no credit card required". Serverless Training API checkpoints can be sampled without any deployment (`fine-tuning/evaluating-fine-tuned-models.md`: "Serverless checkpoint sampling"). Sampling is billed per token (Muse Glimmer 30B: prefill $1.96/M, sample $4.88/M), roughly $0.15 for the 200-row test set, charged to the inference ledger. Rule 4 allows "other training only if the docs and the job creation page confirm it is free", which this does. Plan: LoRA rank 8, 1 to 2 epochs over the SFT file (≤ 100k training tokens), `save_weights_for_sampler`, score the checkpoint with `score.py`. Requires Python 3.11 (`fireworks-ai[training]` refuses 3.10); installed via pyenv into `venv311/`.
   - Smallest-model paid job: the brief says "smallest tunable model under 16B". The literal smallest is qwen3-0p6b (0.75B). I chose **qwen3-4b-instruct-2507** instead: it is the smallest instruction-tuned base that plausibly serves a code-generation task, and the job cost difference is under 5 cents (~100k tokens × $0.50/M). Since the result cannot be scored tonight either way, the choice only affects what Raheel can deploy tomorrow.

7. **Reasoning tokens.** From sibling notes: `reasoning_effort: "none"` works on nemotron-lightning, deepseek-v4p1-flash and kimi-k3; GLM 5.3 / 5.3-flash reject "none" but "low" gives ~0 hidden tokens; gpt-oss-120b accepts "low". The baseline sweep uses plain prompt + these settings with max_tokens 512, so a model's reasoning budget is not what we are measuring. Recorded per run in the results JSON (`reasoning_effort`).

8. **Routing confidence signal.** Rather than a second prompt, I use the geometric-mean token probability of the small model's answer (`logprobs: true`), which costs nothing extra, and sweep thresholds offline against the already-collected large-model results. Escalation also fires on any invalid (non-compiling) answer.

9. **Account suspension (22:04 PT).** Every call returned HTTP 412 "Account raheeldeal is suspended" with `Suspend State: CREDIT_DEPLETED, Balance USD 0.00` (monthly-spend quota shows $1.66 of $50 used, so it is the prepaid balance, not the limit). Only the account owner can add funds. The runner now treats 412 as a hard stop. All API-free phases were completed while waiting; paid phases are marked partial in RESULTS.md until credit is restored.

10. **Rate-limited rows are repaired, not scored as misses.** The account's serverless rate limit is shared by ten concurrent sessions tonight, so 2 to 10 rows per baseline run came back HTTP 429 even after 5 retries. Scoring those as wrong would measure the account, not the model. `run_eval.py --repair <results.json>` re-queries only rows whose request errored (same model, prompt, max_tokens, reasoning setting), rescores them and recomputes the aggregates; the ledger gets a `<prompt> repair` row and the file gets `repaired_rows`. Retries are now 8 with jittered backoff up to 60 s. Pre-repair numbers are in `raw/logs/base_*.log` for comparison (nemotron 34.0 → 35.5, deepseek 64.0 → 64.5, glm-flash 67.0 → 68.0, glm-5p3 57.5 → 60.0, gpt-oss 71.5 → 73.5, kimi 63.0 → 65.0).

11. **glm-5p3 re-run at max_tokens 2048 (`_mt2048`).** With reasoning_effort "low" the model still spent the whole 512-token budget thinking on 10 of 200 rows and returned an empty answer. The protocol floor is 512+, so the fair frontier number is the 2048 run; the 512 run is kept as evidence of the cost of hidden reasoning. kimi-k3 and the small models had 0 or 1 truncations at 512.

12. **The rubric prompt (`prompts/v2_rubric.txt`) was written from gpt-oss-120b's baseline misses on the test set itself.** That is what the protocol asks for ("rules learned from baseline misses"), but it means the +20 to +27 point jump is partly the prompt learning the KB13 annotation conventions (a "word" is [A-Za-z]+, "between" is order-free, "contains" is unanchored). To show it is not just memorizing the 200 rows, the same prompt is also scored on 100 held-out train rows that were never looked at while writing it (see RESULTS.md "Held-out check").

13. **Muse Glimmer is sampled with a ` to=user<|message|>` prefill.** Its chat template answers on channels; left alone the base model opens `to=self` (reasoning) and burns the whole budget. The prefill forces the answer channel, which is the same reasoning-off condition the serverless models get. Base and LoRA are sampled identically, so the SFT delta is attributable to the weights. The SFT target includes the ` to=user<|message|>` tokens, so the tuned model is also trained to answer directly.

14. **Managed qwen3-4b SFT: documented, not run.** `bash sft_managed.sh` stops at `firectl dataset create` with "BLOCKED: mutating command ... cannot run inside an AI agent"; a sibling session also found dataset uploads 403-disabled on this account. Since the result could not be scored without a dedicated deployment (rule 3), nothing is lost for the headroom question; the row stays "not scored (dedicated deployment required)".

15. **Frontier comparison uses the same rubric prompt.** The headroom question is "best small config vs frontier", and comparing a tuned prompt on the small model with a plain prompt on the frontier would flatter the small model. Both glm-5p3 (2048 tokens) and kimi-k3 (100 rows) were re-run with `v2_rubric`; those are the frontier numbers quoted in RESULTS.md. Cost of the two runs: $0.49, the biggest single item in the ledger.

16. **SFT outcome.** The training SDK's `forward_backward` result carries metrics as `loss:sum` and `response_tokens`, not a `loss` field, so the step log prints `loss None`; the per-token loss is recomputed from the stored metrics in RESULTS.md. The slot wait was 23 attempts (50 minutes); the run itself took about 4 minutes. The checkpoint path is in `results/sft_checkpoint.json`.
